Every choice made while building unattended, why, and what is configurable. Open questions for the coach are at the end.

## Build environment

- **Node.js was not installed system-wide** (the brief expected Node 24). An official Node v24.19.0 binary, signed by the OpenJS Foundation, was already on the laptop inside the Codex runtime cache (`~/.cache/codex-runtimes/.../node.exe`). It was copied into `tasuki-cards/.tools/node/`. npm 11.21.0 was downloaded from registry.npmjs.org (sha512 integrity verified) into `tasuki-cards/.tools/npm/`. After installing Node 24 LTS normally, `npm install` and `npm run build:single` work without `.tools`.
- **Pinned dependency versions**, each published at least two weeks before the build (exact versions in `package.json`). **Vite 7.3.7, not Vite 8**: Vite 8 bundles with Rolldown, while `vite-plugin-singlefile` 2.3.3 needs Rollup 4, and the single-file HTML is a hard deliverable. TypeScript 5.9.3 (most widely compatible), React 19.3.0, Dexie 4.4.6, Vitest 5.0.3.
- npm 11's new install-script gate skipped esbuild's `postinstall` (a binary self-check only). The platform binary `@esbuild/win32-x64` installs as an optional dependency and was verified to work.

## Age-grading tables (spec 3.4)

- **Source:** Alan Jones road age-grading standards, public domain, https://github.com/AlanLyttonJones/Age-Grade-Tables, cloned to `C:\Users\finga\Documents\tasuki-cards-data`.
- **Commit:** `4aac6737cb9f216c90a0a610355667cd3d921c61` (committed 2025-07-27, "Updated AgeGrade.1mi file for RunScore").
- **Files:** `2025 Files/MaleRoadStd2025.xlsx` (sheet `AgeStdSec`, "Version 2025-07-27") and `2025 Files/FemaleRoadStd2025.xlsx` (sheet `AgeStanSec`). These are the most recent road standard tables (2025, approved by USATF MLDR on 2025-01-10).
- **Converted** on 2026-10-22 by `scripts/convert-age-tables.mjs` (dependency-free xlsx reader) to `src/engine/data/ageGradeRoad2025.json`: ages 5–100 in single years, 22 distances from 1 mile to 200 km, standard times in whole seconds. Re-run with `npm run convert-tables`.
- The clone succeeded, so age-graded ratings are **not** provisional. The spec's fallback table is still implemented (Settings → age-grade table → "fallback (provisional)") and, when selected, marks every age-graded rating provisional.
- Spot checks (also unit tests): M14 5 km = 800 s, M25 5 km = 769 s, F12 5 km = 945 s, F25 5 km = 834 s, M50 10 km = 1783 s. The open 5 km standards (769 / 834 s) match the spec's fallback values.
- Interpolation follows the spec, not the source spreadsheet's internal method: log(time) against log(distance) between adjacent table distances; extrapolation below 1 mile along the 1 mile–5 km slope (so the 1.30 km Campus Circuit is extrapolated, e.g. M25 standard ≈ 180.4 s); linear in decimal age between single-year rows; ages below 5 use age 5.

## Data model (spec 2)

- The spec's `Event` type is called `TasukiEvent` in code, to avoid clashing with the browser's built-in `Event` type.
- `Performance` has an optional `courseId` (and an optional `terrainFactor` override). Quick Entry picks a course directly, and a stat such as SPD needs to know which course a Circuit result was run on. Resolution order: performance course, then the event's course.
- **Deleting a performance is a soft delete** (`deleted: true` plus a history entry with the reason). It is ignored by every calculation but kept, because the spec says corrections are never destructive.
- **Circuit participation is derived** from Circuit performances, not stored, so correcting or deleting a Circuit result can never leave a stale participation record. Only `saturday_run` and `freeze` participation is stored.
- `Athlete.yearGroupYear` (optional) records which academic year the year group refers to. Age estimates for results from earlier years then use the age the athlete had at the time. If absent, the academic year of the as-of date is used.
- Every record created by "Load demo data" carries `demo: true`, so "Clear all demo data" removes exactly those records and nothing imported.
- Outsiders (non-roster competitors in pasted results) are never stored. Only the field size and each category winner's time (no name) are kept on the event.
- `displayMode: 'first_initial'` shows "Aiko T."; `'alias'` shows the public alias, or the first-initial form if no alias is set.

## Scoring (spec 3)

- **Months old (freshness, spec 3.7)** means whole calendar months elapsed (a result from 15 Jan is 6 months old on 15 Jul). Ratings step down once a month rather than drifting daily, which is easier to explain to students.
- Course records and year bands use the athlete's year group **at the time of the run**, which is the recorded year group shifted by the number of academic years.
- **Which stat a result feeds is decided by the result's kind**: circuit → SPD, climb → CLB, descent → DSC, nav → NAV, bleep → END, arm → ARM. Race, relay leg and parkrun → RACE, plus END when the effective distance is ≥ 5 km; a long run feeds END only. The course supplies distance, climb, terrain and benchmark mode. Go-live (5 Nov 2026) adds race pathways, below.
- **Only verified, non-deleted results count**, for every stat. The spec says "verified" for RACE, END and the NAV reference; this extends it to all stats, so a student-reported result never moves a rating until the coach ticks it. Every result still appears in the Career Vault with the reason it does not count ("unverified", "not a clean run", "set this course's benchmark in Settings", …). Results dated after the as-of date are ignored, so as-of views are reproducible.
- **Fixed-benchmark courses** (3.6): with no benchmark for the athlete's sex, the stat is locked with exactly "set this course's benchmark in Settings". A descent with no course at all is unscored ("no course set"), because there is nowhere to set a benchmark. Fixed scores are provisional only if the age-grade table is. The reference distance (5 km) and age (25) are config values.
- **Growth Shield** (3.8) applies to the six OVR stats, not to RACE. RACE is a weighted blend of up to three races, and lifting it to one race's peak would distort it. When the shield lifts a stat, the card shows the date of the peak result behind it. "Last 12 months" means fewer than 12 whole months old.
- **ARM has no freshness decay**: the 12-month best-level window replaces it, since 3.9 says ARM never falls on a bad retest. A domain measured below level 1 counts as level 0 ("measured"), and ARM is then clamped to 40–99. A single ARM test gets its own score only if it measured all three domains, but partial tests still count towards each domain's best level.
- **NAV**: a blank error count means 0 errors. The reference pace is the best-ever verified Circuit pace (time ÷ effective distance) up to the as-of date, including results too old to count, because the spec says "best-ever" and "a PB". With no Circuit, the best verified race, relay leg or parkrun of 5 km effective distance or less is used. The 0.5 efficiency floor is a config value.
- **Rounding**: every 40–99 score rounds half up, with float noise removed first (69.49999999 → 70).
- **Ties** between best results: highest FreshScore, then the higher unpenalised score, then the most recent. For END, an exact tie between bleep and long run goes to the bleep. The END label uses the raw distance ("from 10 km, 12 Aug").
- **Bleep**: above P95 the percentile is reported as 95, and the rating rises linearly from 96 at L_P95 to 99 at 1.2 × L_P95. Under-11s use the age-11 row and 18+ the age-18 row, as the spec says.
- **Lock hints** (≤ 3 words on the card) say why a stat is locked, most actionable reason first: "Benchmark not set", "Run the Circuit" (also used for NAV with no reference pace), "Clean descent run", a result waiting to be verified, a last result over 24 months old, or the default ("Bleep or 5K+", "Run a climb", "Complete a nav", "Test all three" / "Test calf", "Race to unlock").
- **Provisional marker**: shown on a stat when the result behind its displayed value rests on a provisional table or formula (bleep table, NAV, ARM thresholds, or the fallback age-grade table). Locked stats never carry it.

## Streaks, Surge, PBs, In-Form, badges, handicap (spec 3.10–3.14)

- **Streak weeks** count verified Circuit results and stored Saturday-run participation. A holiday week is always "holiday" (it neither counts nor breaks), even if the athlete ran a Circuit that week. A verified parkrun or long run in a holiday week earns the holiday-bonus flame.
- **Freezes**: one per half-term, taken in week order. A freeze on a week that already counts, or on a holiday week, does not use up the allowance. **A freeze in a week that no half-term covers is not honoured**, so half-terms must be set in Settings, and the Settings page warns about this. The current, in-progress week is never treated as missed.
- **Surge baselines** are race, parkrun or Circuit results from 1 to 90 days before the relay. The same day is excluded, and a relay leg or long run is never a baseline. Relay legs with no time or distance are left out. The sanity gate groups legs by event and effective leg distance (to 0.01 km).
- **Surge sanity gate: minimum group size (a new constant).** Taken literally, a runner alone on their leg distance is their own median, so any surge above +2.0% would be cut to exactly +0.7% and could never medal. In a one-team ekiden every leg distance is a one-runner group, so the gate would remove every Surge. The gate therefore applies only to groups with at least `surge.sanityMinLegs` legs that have a baseline (default 3, editable in Settings). This is open question 1 for the coach.
- **Raw PBs**: by course (`course:<id>`) for course runs, and by distance (`dist:5.00`) for races, parkruns and long runs without a course. Relay legs (they have Surge), NAV runs (times depend on errors and variants) and descents that were not clean runs are excluded. A run whose distance differs from its course distance (e.g. a 5.2 km long run on the 1.3 km Circuit) is filed under its distance, not the course. Equalling a best is not a PB.
- **In-Form** window: the as-of date and the six days before it (7 calendar days). A first-ever result is not In-Form, because there is nothing to beat. A card shows the raw PB first ("PB −12 s"), otherwise the score improvement ("SPD 71 → 74").
- **Parkrun distance**: a parkrun entered without a distance is taken as 5 km at entry time (`input.parkrunDefaultKm`).
- **Course records** use results up to the as-of date. On a tie the earlier holder keeps the record, and the year band is the athlete's year group at the time of the run.
- **Badges** are permanent achievements, so they use all-time data. Streak milestones come from the best streak (dated by the week it was reached), and the ARM badge shows the highest level ever reached in each domain. Distance and Mountain badges count any verified run that covered the distance or climb, including relay legs and long runs. The card's five-badge row takes the most prestigious badge of each kind first (record, Surge gold, expedition, Mountain, …), so one long streak cannot fill the row.
- **Handicap start sheet**: each PB is the all-time best verified Circuit time. Offsets round to the nearest 5 s (halves round up). Runners with no PB start in the first wave. Rows are listed in start order.

## Input: time parsing and name matching (spec 3.1, 4.2)

- **A time column vs free text.** In a time column, `16.15` reads as 16:15 (with a warning). In free text a dotted number may be a distance, so it is not read as a time. `16.5` is rejected as ambiguous (16:05? 16:30?), and `16.75` because seconds must be under 60. Nothing is guessed silently: every rejection says why.
- **Excel hazards**: Excel turns a typed `16:15` into `16:15:00` (16 hours). A three-part time of 10+ hours with :00 seconds is accepted with a warning, and the pace check catches the rest.
- **Free-text guards**: numbers after `place`, `leg`, `climb`, `ankle`, `calf`, `stork`, `laps`, `errors`, `field` and year groups such as `Y9` are not times. Neither are clock times (`8:10am`), Forms timestamps or paces (`3:15/km`). A lone `m` means metres in free text unless it clearly means minutes (`16m15`).
- **Dictation**: "seven fifty five" = 7:55, minutes then seconds, as the spec says. A bare number such as "755" or "1615" is never read as a time; the error suggests "16:15". Kanji numerals (十六分十五秒) are read in a single time field but not in free text, because many Japanese names contain numeral characters.
- **Pace check**: faster than 2:30/km or slower than 12:00/km is flagged; exactly on the limit is fine. The paste review uses the effective distance, so a steep mountain race is not flagged as implausibly slow.
- **Name matching ladder**: exact stored alias → normalised (either order, any script, hiragana ≡ katakana, kanji only via a stored alias, spaces ignored for kanji and kana, punctuation dropped by timing systems tolerated) → initials ("Ken S", "H. Mockridge", "M. J. Example") → fuzzy (Jaro–Winkler ≥ 0.88, suggestions only, up to 5) → unmatched or outsider.
- **Never a confident match**: a given name or family name on its own; two athletes matching at the same level ("two athletes matched"); a stored alias that is another athlete's real name. Inactive athletes are matched only if no active athlete matches, and a warning is shown.
- **Alias learning** refuses strings that would cause trouble later: the athlete's own initials or a bare name part, and anything that already identifies another athlete.
- **Duplicate detection** (roster import) compares names in either order, including aliases, in the same academic year, so a Y9 recorded last year is caught as a duplicate of a Y10 import this year.
- Not supported, by choice: run-together initials ("MJ Smith"), honorifics ("先生", "さん"), and treating romanisation variants (Oono, Ohno, Ōno) as equal. These show as fuzzy suggestions and are learned as aliases once confirmed.
- The spec's example names in the line format (4.3) may belong to real people, so the in-app Help, tests and demo data use obviously invented names instead (Aiko Testfield, Ben Sampleton, Coach Example). The line structure is identical.

## Input screens (spec 4, milestone 2)

- **Review-table statuses**: each pasted row is *Import* (confident match), *Check* (a fuzzy suggestion, an unmatched name in line format or Forms, two athletes matched, or an implausible pace), *Skip* (missing time, duplicate row, already-saved duplicate), or *Outsider*. Only *Import* rows are saved, and only when the coach presses Approve.
- **Outsiders**: in a pasted results table (website, PDF, Excel), a name that matches nobody and has no fuzzy suggestion is an outsider by default. In line format and Forms exports every name should be on the roster, so it is *Check* instead. Outsiders are never stored. They count towards the event's field size (the larger of the row count, the highest place and any field size given), and the fastest time per category (or "Overall") is kept on the event without a name.
- **Duplicates**: a row is a duplicate of a saved result when the same athlete has a live result of the same kind on the same date within 1 s (or the same laps). It defaults to *Skip*; the coach can still tick it.
- **Alias learning** happens only when the coach confirms a match the matcher was not sure of (fuzzy, ambiguous, unmatched, or a different athlete chosen by hand). The exact spelling is stored as a new alias unless it would clash with another athlete.
- **Events**: pasted results join an existing event when the name and date match (or when the coach picked the event above the text box). Otherwise one new event per header is created on approval. Circuit, climb, descent and nav headers find their course by `course <name>`, then by the event name. If there is exactly one Circuit course, a `circuit` header uses it.
- **Forms exports are always saved unverified** (source `form`), and so are line-format rows marked `unverified`.
- **Quick Entry** has a "Saturday run (attendance only)" option that records streak participation. Its live preview derives everything with and without the draft result and lists only what changes for that athlete: stats, PBs, In-Form, tier, streak and new badges.
- **Corrections need a reason**; delete is a soft delete with a reason and can be restored. The full history (who, when, before → after, reason) shows in the correction dialog.
- **Voice dictation** uses the browser's own speech recognition (Chrome sends audio to its speech service, so it needs internet; this app stores no audio). It only types into the Paste box for review. It is hidden in browsers without the API.
- **Test runner uses one worker** (`maxWorkers: 1`). This laptop runs close to its memory commit limit (about 0.3–0.8 GB free with the usual apps open), and parallel test processes crashed with out-of-memory errors.
- For the in-app browser preview, a launch config was added at `C:\Users\finga\Documents\.claude\launch.json` (it points at the project-local Node and Vite). It is not part of the app.

## Cards, avatars, printing (spec 5, milestone 3)

- **Card layout** is sized entirely in millimetres (63 × 88 mm), so the printed card matches the screen. From top to bottom: OVR box (with n/6), tier · year, display name, the RACE banner (rating, ★ caps, best race line), the avatar on a diagonal tasuki sash, six stats in a 3 × 2 grid with the date of the result behind each one (top right of each cell), streak flame plus holiday-bonus flames, up to five badges, and the footer. Long names shrink to fit rather than being cut off.
- **Styles**: Bronze (copper), Silver (steel), Gold (gold), Icon (deep violet with gold), and In-Form (a flame-orange frame with an "IN-FORM · PB −12 s" tag, kept for the week). The design is original: a vertical card crossed by a striped sash, with no shield shapes or layouts from existing trading-card or video-game designs.
- **Avatar**: one flat-colour runner in mid-stride with anime-inspired proportions. Every athlete has the same body; only skin tone (6), hairstyle (8), hair colour (6), kit colour (academy navy/red plus six generic house colours) and an accessory (cap, headband, glasses) vary. The default comes from a hash of the athlete id. Earned extras are drawn on top: compass in hand or floating, ankle guards, armour glow, motion lines, lightning trail, contour-line wings, dust burst, the tasuki sash (plain, or gold-edged from 3 caps), a flame on the sash for a Surge medal, and a red headband with tails for an 8-week streak.
- **Print geometry**: 3 × 3 cards with 3 mm gutters for crop marks, centred on A4 (7.5 mm side margins, 13.5 mm top and bottom), so nothing falls in a printer's unprintable edge. Card sheets use a named CSS page (`@page cards`, zero margins), so board printouts keep their own margins. Provisional markers and DOB never print.
- **Automated print check** (`npm run check:print`, after `npm run build:single`): headless Chrome (the installed one, via puppeteer-core) loads demo data through the real UI, opens the print studio with every card selected, and checks that every card is 63 × 88 mm and inside its A4 sheet, that no text element overflows its box, that locked stats show no numbers, and that provisional markers are hidden in print. It then prints a real PDF and checks one A4 portrait page per sheet. The PDF and a picture of sheet 1 are saved in `test-output/`.

## Boards (spec 6, milestone 4)

- One board component renders the same content on screen, in projector mode and in print. Absolute boards (RACE, SPD, course records, END, caps) show the top 10, with a "show everyone" switch, and leave out opted-out and inactive athletes; the coach view lists who was left out. In-Form, Streak and Surge boards show everyone active.
- Ties share a rank (1, 2, 2, 4). The SPD board shows raw best Circuit times from the last 24 months, grouped by sex and year band using each athlete's current year group. Course records use the year group at the time of the run, and an opted-out record holder appears as "Record holder (private)".
- **Projector mode** is a separate full-screen dark page with very large type, readable from the back of a room. ← and → change board, C (or the button) cycles through all boards every 20 s, F goes full screen, and Esc exits. The controls fade until the mouse is over them.
- **Printing boards**: choose A4 or A3 on the Boards page, then Print. Boards use their own named CSS pages with 12–14 mm margins, independent of the card sheets.

## In-Form, streaks, Surge, handicap, badges UI (milestone 5)

- **In-Form** shows on the card (special frame and "PB −12 s" tag), on the In-Form board, on the Home page, and as a Print Studio filter ("In-Form this week").

## Settings, help, polish (milestone 6)

- **Scoring constants editor**: every value in the config object is editable, grouped by spec section. That includes the bleep table row by row, the fallback age factors and the badge distances. Editing shows a live **impact preview** (how many ratings change, for how many athletes, the largest change, and a full list) before anything is applied. Applying creates a new config version with an optional note. Earlier versions can be loaded back into the editor and re-applied, which creates a newer version, so history is never rewritten.
- **No network at runtime**: the single-file build contains no external scripts, styles or fonts (system fonts only: Bahnschrift for numbers, Segoe UI / Yu Gothic UI / Meiryo for text). Dictation is the one feature that depends on a browser service.

## Go-live changes (coach's review, 5 Nov 2026)

- **Race pathways (plan 1).** A verified race, relay leg or parkrun of up to `spd.raceMaxKmEff` (3.5 km effort) also feeds SPD, so SPD is the best of the Circuit and short races. **3.5, not the plan's 3.0:** the coach's own worked example (Hachimantai 3K, 3 km + 40 m climb = 3.4 km effort) feeds SPD, which a 3.0 limit would not allow, and almost every 3 km trail race has some climb. A steep short race (say 3 km + 200 m = 5 km effort) still does not count as speed. Change it in Settings → Scoring → SPD if needed. A verified race, relay leg, parkrun or long run with at least `clb.raceMinClimbM` (150 m) of climb and at least `clb.raceMinClimbPerKm` (50 m per km of raw distance) also feeds CLB, scored on effective distance like every timed run (the climb course still counts). Long runs are included for CLB because a hilly training run is still a measured climb; it only counts if it is the best. Both pathways can be switched off in Settings (`spd.allowRaces`, `clb.allowRaces`). A race-based stat is labelled by its event ("from Hachimantai Hill Race, 12 Oct"). The card hints became "Circuit or race" and "Race a hill" (three words at most).
- **Nothing provisional (plan 2).** The coach accepted the spec's bleep table (attributed to Tomkinson et al. 2017), the NAV formula and the ARM thresholds for go-live, unchanged. `end.bleepProvisional`, `nav.provisional` and `arm.provisional` default to `false`. On load (and when a backup is imported), a store whose current config still has any of them `true` gets a new config version with them `false` and the note "Go-live: provisional markers removed", so the change shows in the version history and the impact preview of later edits. The migration runs once: that version carries `migration: 'go-live-2026-11'`, and if the coach later switches a marker back on, it stays on. The fallback age-grade table still marks ratings provisional if it is ever selected.
- **Roster from pasted results (plan 3).** Every review row with no confident match carries a new-athlete proposal: the name as written (results-table capitals such as "YAMADA Hanako" are read as family name first; kanji and kana are split family-first and the written form is stored as an alias so the next table matches exactly), and sex from the sex column or the category (男子/女子, 男/女, M/F, Men/Women, Boys/Girls, Male/Female, Ladies, M40, W35…; "男女混合" or "M/F" give no answer). The coach picks the year group in a dialog (one picker for everyone, or per runner) and can correct the names; the dialog warns about a likely duplicate. One confirmation covers every row with the same name as written, across sections. Athletes are created only when the results are approved, with the same defaults as a typed-in athlete (first name + initial display, default avatar, `yearGroupYear` = this academic year). **Our school** names live in app meta (`meta.ourSchoolNames`, Settings → Data), not in the scoring config, because they do not change any rating; until the coach edits them they default to the coach's examples (Harrow, ハロウ, 安比, Appi). An outsider whose club column (所属 / Club / Team / School) contains one of them, ignoring case, width and spaces, becomes "our school" (status *Check*) and is offered with **Add all N academy runners**.
- **The working behind every rating (plan 4).** `src/engine/explain.ts` (`explainStat`, `explainOvr`, `explainAll`) writes the explanation from the derived ratings: it names the stat's own basis result (it never picks a "best" differently from `stats.ts`) and quotes the same engine numbers (effort, standard time, age grade, Run Score, bleep percentile, fixed-benchmark age adjustment, NAV prediction and efficiency, ARM levels, freshness, Growth Shield, RACE weights). It takes the lookup as an extra argument (the plan's signature had no way to name courses and events). Every result meant for the stat is listed with a reason: used, Growth Shield, lower, older (higher before freshness, lower after), equal, over 24 months old, waiting to be verified, not scored (with the engine's reason), not in the top three, outside the ARM window. A unit test runs it over every demo athlete in both versions and checks that the headline matches the card and the text never contains "undefined" or "NaN". **Student version** (athlete page → Student version, printable and copyable): display name only, ages in whole years, never the date of birth or the full name of an athlete shown by initial. The coach view gives ages to one decimal, as in the coach's example. The athlete page's results table gained pace (over the raw distance), effective distance, standard time, age grade, score before freshness, freshness penalty, the score that counts today and the stats fed.
- **Descent benchmarks "against Mr Loke" (plan 5).** Course editor (fixed-benchmark courses) → **Set the benchmark from a reference run…**: pick the runner (staff first), their time (or one of their results on the course), the date and what the run should score (default 90). The spec 3.6 formula run backwards gives that runner's open time, t99 = score × time ÷ (99 × ageAdj), with the age adjustment for their age on the run date (a staff member without a date of birth is taken as 30, and the preview says "estimated": add a date of birth for an exact age). The other sex's time is scaled by the ratio of the open standards at the fixed-benchmark reference distance and age (Std(25, F, 5 km) ÷ Std(25, M, 5 km) = 834 ÷ 769 = 1.0845, from config, not hard-coded). Times are rounded to whole seconds, so the reference run scores the chosen value (shown in the preview). A one-line note ("Benchmark from a reference run: … ran 5:00 on 4 Nov 2026 (M, age 40.5), set to score 90 …") replaces any earlier such line in the course notes, and the DSC explanation quotes it. Race descent profiles stay out of DSC, as the coach said.
- **NAV from orienteering results only (plan 6).** The reference pace is still the best-ever Circuit pace, else the best race, relay leg or parkrun pace up to `nav.refRaceMaxKmEff` (5 km effort). With neither, each nav result gets a reference predicted for its own route from a verified race of any distance: T_route = T × (route ÷ race D_eff)^`nav.riegelExponent` (1.06), on effective distances. "Best recent race" = the race, relay leg or parkrun not older than `freshness.expireMonths` (24) that predicts the fastest route time; this is the Riegel model's own idea of "best", so it needs no age or sex. Long runs are not races and never set the pace. The NAV lock hint is now "Run any race". The explanation shows which race set the reference and the scaling. Score-O (`points <n>` and a time limit) is left for later, as the plan says: enter a score-O as the coach's measured route km.
- **Drop in files (plan 7).** Paste & Match accepts a dropped file, or **Choose a file…** (also works where dragging does not). `.csv`, `.tsv` and `.txt` are read as text: UTF-8 (a BOM is dropped), else Shift_JIS, because Excel on Japanese Windows saves CSVs that way. `.xlsx` reads the first sheet with no library (`src/engine/parse/xlsx.ts`): a zip directory walk ported from `scripts/convert-age-tables.mjs`, with Chrome's own `DecompressionStream('deflate-raw')`. Cells formatted as times become times as Excel shows them (mm:ss → "16:15"; h:mm → "16:15:00", so a time typed as hours is caught by the existing 10-hour warning), dates become YYYY-MM-DD, numbers lose float noise, shared and inline strings are decoded (phonetic guides dropped). Tested on real files written by openpyxl and LibreOffice (`src/engine/parse/fixtures/`). Old binary `.xls` files and PDFs are refused with what to do instead (save as .xlsx or CSV; copy and paste from the PDF viewer). One file at a time.

## Next-5K prediction, booklets and ekiden write-ups (11 Nov 2026)

- **Prediction** (`src/engine/predict.ts`, constants in `config.predict`): every verified timed result of at least 0.5 km effort from the last 18 months is converted to 5 km with a youth-adjusted Riegel exponent: b = 1.115 at 11 down to 1.063 at 18 (from 3 km), plus 0.008 from 2 km, 0.015 from 1.5 km, 0.025 from 1 km and 0.04 from 0.5 km. It is then brought forward for natural maturation since the result (boys 3.6%/yr at 11 down to 0.2% at 18; girls 2.1% at 11, 0 at 14). The results are combined by inverse-variance weighting on log time, with uncertainty growing with the distance gap, the kind of result, unofficial timing and age. If the results disagree more than expected, the interval widens (chi-square inflation). A projection 12% or more slower than the fastest is treated as not a full effort and listed, not used. The interval is 90%; ±3% or less is "high" confidence, up to 6% "medium", otherwise "low".
- **Targets**: one term (0.3 of a year) of maturation plus the term training gain for the squad's tier (club, 3–4 sessions a week: realistic 1.2%, stretch 2.1% faster in 5 km speed; tiers for PE, intro and academy in config). A target is never slower than an actual 5 km PB in the window: then the realistic target is the PB and the stretch target beats it.
- **Source of the constants**: the coach's research synthesis (Nov 2026). Its Japanese national-average tables are marked by the report itself as parameterised rather than read from e-Stat, so they are **not used** until the raw e-Stat Excel files are loaded. The exponents, maturation rates and training gains are model assumptions, shown in every explanation.
- **Unofficial events** (a training relay, a stopwatch time trial: `unofficial` in the line format) feed SPD, END, CLB and the prediction, but not RACE, and earn no race cap. Two legs of one relay are one cap.
- **Two relay legs by one runner** in the same relay are no longer flagged as a duplicate.
- **Results booklets** (the ISTS layout used at Hachimantai XC) and **ekiden write-ups** ("Team (1st, general): 34:25" then "Name (9:18) → Name (8:26)") are recognised in Paste & Match and rewritten into the table and line formats (`src/engine/parse/booklet.ts`). Each booklet category becomes its own event, with distance, club (our school flagged) and category (sex).
- **The card footer** shows the realistic next-5K target when there is one.

## Placings, parkrun, handicap and the Silly Lab (13 Nov 2026)

- **parkrun is not a race.** RACE (and race caps) are races and relay legs at official events. A parkrun still feeds SPD, END and the 5K prediction, and has its own parkrun badges. RACE measures how good the best races were (age-graded, top three weighted 50/30/20), not how many: racing more earns caps and badges, never RACE points, as in the original spec.

In a table that has times, a missing time is still an error. Non-academy runners are counted, never stored.

- **Event pages**: a field strip (fastest on the left, last finisher on the right) with our runners on it, top % and the gap to the winner. Event names are links everywhere (athlete results, the stat basis, Home).

Most items are free; a few are earned from the data (crown: Gold; summit flag: Icon; halo: 8-week streak; rocket boots: SPD 80+; giant compass: NAV 75+; kamoshika: CLB 70+; trophy: a course record or a gold Surge; expedition pack: an expedition badge; shooting stars: In-Form; pace robot: a 5K prediction). **Surprise me** picks a random outfit from what the runner can wear. ## Evidence-weighted OVR, standards below the mile, September rollover (16 Nov 2026)

Three faults the coach reported after loading the Green Long Ducker and a 550 m time trial.

- **Year groups were a year behind.** Pupils created from the 2025 Long Ducker workbook were stored with the year group in the workbook (Y9, for 2025) and shown as Y9 in November 2026. Ages were right (the engine already knew the year group referred to 2025); the label, the year-band filters and the boards were not. Fix: `yearRollover` (`src/engine/display.ts`). On load, and when an import creates athletes from an earlier year's results, any year group recorded for an earlier academic year moves up to the current one and the record is restamped. Y9 for 2025 and Y10 for 2026 give the same estimated age, so no rating changes. This also answers the old open question: year groups now roll over by themselves each 1 September. Leavers (anyone who would be past Y13) keep their record as it was, so their old results are still aged correctly; the athlete page says "left school".
- **Short time trials were scored too generously.** The Alan Jones road tables start at 1 mile. Below that the app carried the mile–5 km slope downwards, but pace rises much faster over short distances (anaerobic energy), so the 550 m standard was 10% too slow for adults and about 13% for a 14-year-old, and every short time trial scored that much too high. Fix: below the mile, the runner's own mile standard (age and sex) is scaled along the track world records from 200 m to the mile (`SUB_MILE_WR` in `src/engine/standards.ts`; `config.ageGrade.subMile`). It is continuous at the mile, and nothing at or above the mile changes. The 1.30 km Campus Circuit moves by under 1%. Limit: the age factor below the mile is taken from the mile; young runners are, if anything, relatively better at short distances than that assumes, so short efforts are still slightly flattered. Track age-grade tables (800 m, 1500 m) would remove that.
- **OVR took thin evidence at face value.** OVR was the plain average of the unlocked stats, so one time trial and one Long Ducker place (two stats) could outrank a runner with twenty parkruns. Fix (`statEvidence`, `ovrFrom` in `src/engine/stats.ts`; constants in `config.ovr.evidence`):
  - Each stat's evidence is the number of separate days with a current result feeding it. A day counts 1; a place with no time ×0.5; an unofficial event ×0.75; an effort under 1 km ×0.5; a result over 12 months old ×0.5 (factors multiply).
  - The stats are averaged in proportion to their confidence, c = n ÷ (n + 1.5).
  - OVR = 50 + proven × (average − 50), proven = N ÷ (N + 1.5), N = all the evidence behind the unlocked stats. 50 is about a 40% age grade: an untrained pupil.
  - This is ordinary small-sample shrinkage (regression to the mean; the same idea as empirical-Bayes estimates and the rating deviation in Glicko-style ratings). The individual stats are unchanged: SPD still shows what the runner ran. Only the OVR asks how well proven the picture is. The athlete page shows "first estimate", "building" or "proven" with the proven share, and "Why?" shows the arithmetic.
  - Effect: one result per stat is 40% proven; a full six-stat card with one result each is 80% proven; a regular with 20+ results is 93%+ proven and within two points of the plain average. Gold (OVR 75) therefore needs either higher stats or more results than before: Gold has to be proven.
- **Version history.** Both rules arrive as a new config version ("Evidence-weighted OVR; standards below 1 mile follow the world-record curve"), created once on load. Earlier versions are read with the old rules, so their ratings can be reproduced, and either rule can be switched off in Settings → Scoring. The spec's worked examples in the tests run under the old rules; `src/engine/evidence.test.ts` covers the new ones.

## Winter Mode (17 Nov 2026)

The coach asked for a light, science-backed way to keep the squad (and himself) fit over the holidays and the snow season, borrowing Duolingo's streak habits without encouraging overtraining. Built in `src/engine/winter.ts`, `src/engine/parse/topUps.ts`, `src/ui/pages/WinterPage.tsx`; constants in `config.winter`; the winter weeks in `calendar.winter`.

- **One rule for everyone ("Rule of 2")**: a winter week is kept with 2 sessions, at least one a run of 15+ minutes; one armour or gym session can be the other. Staff: 3. Maintenance research (Hickson; Spiering et al. 2021) says fitness holds on much less volume if some intensity stays, so the only bonus is the ⚡ for race-pace surges or strides; volume earns nothing.
- **Weekly, capped, asymmetric**: daily streaks reward junk miles; extra sessions earn nothing; a kept holiday week adds to the main streak while a missed one never breaks it. One rest pass per winter is used automatically (Duolingo's equipped freeze); a coach freeze also holds a winter week. In term-time snow weeks a missed week counts as missed, as before.
- **Ski days do not count.** Pupils ski anyway, so it would reward nothing new, and ski boots take the running impact away from calves and Achilles, which is why the "ski-boot antidote" (pogo hops, calf raises) counts instead.
- **No "Frost Shield" on card stats.** One outside suggestion was a shield against winter stat decay. Stats do not decay until 6 months without a result (`freshness.decayGraceMonths`), so a winter costs nothing; a shield would sell protection against a threat that does not exist. Ski days do not feed DSC either: skiing is not descent running.
- **Top-ups never feed ratings, PBs or predictions.** They are self-reported, and treadmill speeds are uncalibrated (the belt can be several % off; 1% incline is the usual match to outdoor running, Jones & Doust 1996). The spring time trial is the honest test. Race pace comes the other way: the runner's realistic 5K target becomes a treadmill speed for surges.
- **Evidence for a session**: a Microsoft Form restricted to school accounts with names recorded (identity from the school sign-in), with an optional photo of the treadmill screen. A live camera feed was considered and not built: it needs pupil logins (pending safeguarding sign-off), would film other people in a gym, and a still photo of the screen proves the same thing.
- **Load nudges, not locks.** First week back after 14+ days: runs of 20 minutes, easy. A week with more than 1.5× the previous four weeks' average (and over 60 minutes): ease off. Soreness 4+: armour instead of a run. Coach to-do: soreness 6+, or over 240 running minutes in seven days. The thresholds are deliberately generous: the acute:chronic workload ratio is disputed as an injury predictor (Impellizzeri et al. 2020), and the "15% weekly jump = 50% more injuries" figure quoted in one suggestion could not be traced to youth data, so the app gives plain advice and claims no risk numbers.
- **Privacy**: soreness, notes and the soreness, pain and volume nudges are left out of the pupils' website copy (health information).
- **House Frost Cup** ranks houses by the share of weeks kept, so nobody is ranked last on their own (the outside motivation review: no public bottom-half rankings).
- **Strava**: we do not compete with it as a GPS logger. Strava is for 13+ (16+ in some places), its maps show where children run, and it has no school team, cards or coach. Tasuki is the team layer: a Strava or watch screenshot is accepted as the photo like a treadmill screen.

### Second outside spec (Gemini "maintenance engine"), checked against the code

Taken:
- **Sessions count on separate days.** Two runs (or a run and armour) on the same day are one session, so a week cannot be saved by cramming on Sunday. Dates carry no clock time, so "different day" stands in for the suggested 36 hours.
- **A thin fortnight is a break.** The first-week-back advice now also fires when there were under 20 running minutes in the 14 days before this week, not only after 14 days with no run at all.
- **Where it is sore.** The form asks; heel or knee soreness of 4+ in Y7–Y10 goes straight to the coach with no session suggested (Sever's and Osgood–Schlatter are common at these ages and need a person, not an app). Elsewhere, 4–5 is still an armour swap.
- **Session cards** (`src/engine/winterSessions.ts`): easy run, sharp run, treadmill surges, ski-boot antidote, sore-legs armour, staff tempo. Each runner's page shows the one that fits their week, with their own treadmill speeds.

Not taken:
- **Readiness decay on card stats** (−1.5 a missed week on END/SPD, −2 on ARM). The numbers have no source, a winter costs nothing in the real ratings (decay starts at 6 months), and the motivation review the coach shared says downward card moves drive pupils away. The flame, the week strip and the first-week-back advice already say "you have not been running".
- **EWMA acute:chronic ratio with a 15% spike rule.** Still the disputed ratio, and at one or two runs a week the exponential averages swing on a single run; `max(4 km, 1.15 × chronic)` would warn a pupil who simply did the Rule of 2 after a quiet week. The plain rule (1.5× the previous four weeks and over 60 minutes) stays.
- **Snow weeks demanding exactly one run plus one antidote.** Two runs also give the impact the antidote replaces; the snow-week suggestion already steers to the antidote.

## Treadmill runs from a photo, and engagement (18 Nov 2026)

The coach asked for more pull in the build (with the research synthesis on youth gamification as the guide) and whether treadmill progress could be logged from a phone photo instead of Microsoft Forms.

**Reading the treadmill console** (`src/engine/treadmill/read.ts`)
- The school's treadmills show four seven-segment LED readouts: distance (km, 3 decimals) and time (min:sec) on top, incline (%) and speed (km/h) below. They are bright, saturated and one colour on a black panel, which makes them easy to read without any OCR library or network: keep the pixels of the display's own hue (thresholds from the photo's exposure, with Otsu's method separating segments from their glow; blown-out white cores kept when their colour surrounds them), group them into readouts, straighten the italic slant, and read each digit from which of its seven segments are lit.
- **Decimal points are not read.** On this console they blur into the next digit; the readouts have a fixed number of decimals, so distance is digits ÷ 1000 and incline and speed digits ÷ 10. A colon is found from its small round dots and only helps name the time readout. Readouts are named by position (two rows of two, found even with the phone tilted), and a colon always means time.
- Tested on the coach's own photo (`fixtures/`, 800 × 450): right at every size from 360 to 2,000 px wide, tilted ±8°, with perspective, at half and 1.4× exposure, blurred, sharpened and saved as a JPEG at quality 25 (19 variants checked while building; the fixture and drawn consoles with every digit, sharp separate segments, blur, upright red digits and small digits are in `read.test.ts`).
- It is a reader for **this console**. Another model with a different layout reads the digits but may name them wrongly; the pupil checks every number before sending, and the coach sees the photo.
- **Why not Forms, or AI reading the photo?** Forms is kept for everything else, but typing four numbers from memory is the boring part, and the photo makes cheating harder and checking quicker. Sending photos to an AI service would put pupils' pictures with a third party; reading on the phone needs no network, no key and no agreement.

**Treadmill sessions** (`PerfKind 'treadmill'`, `src/engine/treadmill/session.ts`)
- **Habit, and END from long runs.** A verified treadmill run of at least `end.longRunMinKmEff` (5 km) of effort, with the incline counted as climb, feeds END, age-graded against the road standards like a long run (`treadmill.feedsEnd`, the coach's call on 18 Nov 2026). It never feeds SPD or CLB (belts differ and the rails can be held, which matters most over a fast or steep effort), nor RACE or the 5 km prediction. Every session keeps the weekly streak going like a Circuit run (`streak.treadmillCounts`), earns the **treadmill km club** badges by total verified km (`treadmill.kmMilestones`: 10, 25, 50, 100, 200), and fills the pupil's "This week" panel. Incline is kept and turned into climb (5 km at 1% = 50 m). "How hard did it feel" is the pupil's own 1–10 (no heart rate: the research note's advice for under-16s); it is stored for the coach and not yet used anywhere.
- Checks: refused if the average is over 22 km/h, over 50 km, dated in the future or more than 14 days ago; flagged for the coach if under 1 km, the display speed is over 22 km/h, the incline is over 15%, or the average and the display speed are far apart.

**Pupils send, coaches approve** (website only)
- Pupils: **Log a run** (📷) in the pupil view. They choose their card once (remembered on the phone), take the photo, check the numbers, say how hard it felt, and send. Only a JPEG crop of the display (≤ 140 kB) is sent. They see their own runs waiting and can withdraw them.
- Coaches: **Home → Treadmill runs to check**, with the crop, the numbers, the sender's school sign-in and anything to look at: typed rather than photographed, a number changed after reading, a sign-in that has sent runs for another card before, a card whose runs came from another sign-in before, a duplicate. **Approve** saves a verified treadmill session (the coach has seen the photo) and remembers the sign-in on the athlete (`schoolAccounts`, coach-only, never published); the inbox record and its photo are then deleted.
- **Database rules** (`firestore.rules`, `match /inbox`): any school Microsoft account may create a log only while the pupil view is open **and** treadmill logging is open (`public/settings.treadmillLogs`, on unless the head coach switches it off; only he can change it). Every field is checked: the sender's uid, email and name must be the sign-in's own; the id must start with their uid; numbers in range; photo bytes ≤ 150,000; server time. No updates. Pupils read and delete only their own; coaches read and delete all. 35 checks on the Firestore emulator pass (`scripts/rules-test/`, needs Java).
- **The offline single file** has no inbox (it never touches the network); there the coach can use **Quick Entry → Treadmill → Read a treadmill photo**.

**A new stat never lowers OVR** (open item 2 below, `ovr.newStatNeverCosts`, `ovr.newStatResults`)
- A stat with fewer than `newStatResults` (2) results is new: it counts in the OVR only if the OVR is higher with it. Every choice of new stats is weighed and the best kept; established stats always count. Unlocking a stat only adds choices, so it can never lower the OVR. The coach's example (two strong stats, then a first ARM test at 55) now keeps its OVR; the ARM stat joins at its second result, or sooner if it would lift the OVR. "Why?" on OVR and the pupil's "This week" panel say which new stat is waiting and roughly the value at which it joins.
- **Not taken: "count only the stats that help".** Tried first and measured on the demo squad: a regular's OVR collapsed onto their best stat (+3 on average, 20 of 26 runners changed, four tier promotions), because rarely-tested stats (ARM is screened twice a year) would stay optional for ever. With the second-result rule, 11 of 26 demo runners gain 1 to 5 points and no tier changes.
- **The research note's other suggestions, and why most were not built:** the 50–99 concave curve, never-dropping stats and an OWA "core plus versatility" OVR would each re-base every rating the squad already has; the 30-pupil micro-leagues need a far bigger squad; kudos and friend streaks need pupils writing about each other, which the safeguarding note rules out. Already in the app: Growth Shield, In-Form (never negative), streak freezes, house cup on effort, climbers, the summit ladder and development focus, top-10-only ability boards.

**Version history.** The rules arrive as one config version, "A new stat never lowers OVR; treadmill sessions keep the weekly streak, and long ones feed END", created once on load (`engagementMigration`). Earlier versions are read with both off, so their ratings are reproduced; either can be switched off in Settings → Scoring (new section: Treadmill logs).

**With Winter Mode.** Winter top-ups (a Forms report of a session) still never feed a rating. A treadmill run sent with a photo of the console and approved by a coach is a different record: of 5 km of effort or more it feeds END (the coach's decision, 18 Nov 2026). Both keep the weekly streak.


## ARM for Season 0: both legs, Hop & Freeze, plate levels (18 Nov 2026)

The coach's Season 0 protocol (Nov 2026): the Lunge (ankle), the Wall (calf, 60 bpm, stopped at 40), the Stork (eyes closed, best of 3, stopped at 30) and Hop & Freeze (80 / 100 / 120 / 140 cm ladder, everyone does it), each leg recorded.

- **Each leg's raw result is stored** (`ArmMeasures.left` / `right`: `ankleCm`, `calfReps`, `storkSec`, `hopLineCm`). The engine works out the weaker side (`armEffective` in `src/engine/arm.ts`); the coach never does. Levels, PBs, badges and the "Why?" working all use it, and the working names the weaker leg.
- **Old records still count.** A test saved before this holds one value per measure, already the weaker side, and a hop yes/no. Those are read as before. In a mixed record, per-leg values win measure by measure. A correction can add per-leg values to an old test; the old fields stay visible in the editor until cleared.
- **One leg only:** that leg is used (better than losing the result; the entry form shows both columns, so this should be rare).
- **Hop:** "yes" when the furthest line frozen is at least `arm.hopGateCm` (120) on **both** legs. "No" as soon as either recorded leg is short of it. One leg at 120+ and the other not recorded is not yet a yes. Balance L5 = Stork level 4 on the weaker leg + hop yes, in the same test, as before.
- **Thresholds:** new default config is calf `[15, 20, 25, 30, 35]` reps and stork `[3, 6, 10, 15]` s; ankle is unchanged and the ARM formula is unchanged (levels added 3→40 … 15→99). Existing stores keep their stored thresholds: the coach changes them in **Settings → Scoring → ARM** before entering results, which makes a new config version so earlier ratings can be reproduced. A stored version from before this reads `hopGateCm` as 120 (it has no per-leg hop lines, so this changes nothing).
- **Line format:** `Name ankle 9.5/11 calf 22/25 stork 6/9 hop 100/120` (left/right). The old `ankle 11 calf 18 stork 22 hop yes` is still read. A lone `hop 120` is refused (it cannot say both legs); a line not on the ladder (e.g. 110) is accepted with a warning.
- **Plate levels next to ARM** on the card (`74 A1·C4·B5`), the athlete page stats table and the line under it, so the number never hides the profile. `0` = tested but below level 1; `–` = not tested.
- **ARM spread** (Settings → Scoring → ARM): for each plate, how many active pupils (staff and inactive athletes left out) sit below L1 and at L1–L5, plus tested and not tested, using each pupil's best level in the window. A plate where more than a third of the tested pupils are at L5 or below L1 is marked "review thresholds". With unsaved threshold changes a second table shows the spread they would give, so the one Season 0 adjustment can be checked before it is applied.
- **Demo data:** the first screening stays in the old single-value format, the retest is per leg, so both paths are exercised.
